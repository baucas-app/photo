# Test-Log 2026-09-27 ~23:33 – Rescan-Button reihte Duplikate ein (jobId-Dedupe)

Bezieht sich auf: docs/DONE.md "2026-09-27 (Teil 8)". Letzter offener Punkt aus dem ml-service/backup-worker-
Abschnitt: "Rescan-Button reiht Duplikate ein (keine `jobId`-Dedupe)".

## Fix
`mlQueue.ts`: `enqueueMlPipeline()` übergibt jetzt `jobId: data.assetId` an `mlQueue.add()`. BullMQ lehnt (bzw.
gibt den bestehenden Job zurück) einen erneuten `add()`-Aufruf mit einer bereits wartenden/aktiven/verzögerten
Job-ID stillschweigend ab - der Rescan-Button (requeued die ganze Bibliothek bei jedem Klick) kann pro Foto damit
nicht mehr mehrere Duplikate gleichzeitig in die Queue stellen. Sobald ein Job abgeschlossen/fehlgeschlagen und
aus der Historie gefallen ist (`removeOnComplete`/`removeOnFail`), wird die ID wieder frei für einen echten
neuen Lauf.

## Live getestet
Kleines Node-Skript gegen die echte lokale Redis-Queue: `enqueueMlPipeline()` dreimal hintereinander mit
identischer `assetId` aufgerufen → `mlQueue.getJob(assetId)` liefert genau einen Job mit exakt dieser ID (BullMQ
erlaubt pro Queue nur eine Job-Instanz je ID) - drei separate Jobs wie vor dem Fix wären hier nicht möglich
gewesen. Test-Job danach wieder entfernt. Build + Vitest (9/9) davor und danach grün.

## Nebenbefund (nicht behoben, nur notiert)
Die lokale Redis-Queue hat aktuell ~60 wartende Jobs angesammelt - vermutlich von den vielen Testuploads der
letzten Stunden, da lokal kein ml-service läuft, der sie abarbeiten könnte. Unkritisch (kein Datenverlust, keine
Fehlfunktion), aber falls der Rescan-Status in der Admin-Oberfläche komisch aussieht: das ist der Grund. Würde
sich beim nächsten echten Start von ml-service von selbst auflösen (Retries/Timeout, siehe `ML_SERVICE_TIMEOUT_MS`
von weiter oben in Teil 8).
