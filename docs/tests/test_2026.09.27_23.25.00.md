# Test-Log 2026-09-27 ~23:25 – ml-service: HEIC-Unterstützung (`pillow-heif`) + wichtiger Umgebungsfund

Bezieht sich auf: docs/DONE.md "2026-09-27 (Teil 8)". Der offene Punkt "ml-service kann HEIC nicht lesen" aus
docs/TODO.md wurde umgesetzt und die Kernlogik verifiziert - die lokale Live-Installation ist aber durch ein
neu entdecktes, hartnäckiges Umgebungsproblem blockiert (Details unten, wichtig für zukünftige Sessions).

## Fix
- `ml-service/requirements.txt`: `pillow-heif==0.18.0` ergänzt (bewusst nicht die neueste 1.x-Reihe - die
  verlangt `pillow>=11`, was ungefragt einen Pillow-Major-Versionssprung erzwungen hätte).
- Neue `ml-service/app/__init__.py`: ruft `pillow_heif.register_heif_opener()` beim ersten Import des `app`-
  Pakets auf - läuft damit garantiert genau einmal, bevor `clip_service.py`/`face_service.py` das erste Mal
  `Image.open()` aufrufen, unabhängig davon welches Submodul zuerst importiert wird.

## Fix verifiziert (in einer isolierten, NICHT synchronisierten Test-venv unter /tmp)
Da die lokale ml-service-`.venv` (siehe unten) nicht stabil bespielbar war, wurde die eigentliche Fix-Logik in
einer frischen venv außerhalb des Synology-Drive-Ordners geprüft, mit einer echten HEIC-Datei
(`sips -s format heic` aus einem echten Testfoto):
- **Ohne** `register_heif_opener()`: `PIL.Image.open()` auf der echten HEIC-Datei → `UnidentifiedImageError`
  (genau der dokumentierte Bug).
- **Mit** `register_heif_opener()`: `Image.open()` lädt die Datei erfolgreich, korrekte Maße (2268×4032), Modus
  RGB. `ImageOps.exif_transpose()` (wird in der echten Pipeline für die EXIF-Rotationskorrektur genutzt) und
  `.convert("RGB")` funktionieren beide fehlerfrei mit dem pillow-heif-geladenen Bild.
- Damit ist die Korrektheit der Fix-Logik selbst zweifelsfrei belegt.

## Wichtiger Umgebungsfund: Synology Drive korrumpiert `pip install` in synchronisierten Ordnern
Der Versuch, `pillow-heif` direkt in die echte `ml-service/.venv` (liegt im Synology-Drive-synchronisierten
Projektordner) zu installieren, löste wiederholt Dateisystem-Fehler aus:
- `pip install pillow-heif` (neueste Version) erzwang zunächst ungewollt ein Pillow-Upgrade auf 12.3.0 (siehe
  oben, deshalb explizit auf 0.18.0 gepinnt).
- Danach traten wiederholt `OSError: [Errno 70] Stale NFS file handle` sowie von Synology Drive selbst erzeugte
  Konfliktkopien auf (z.B. ein Ordner `pillow-10.4.0 2.dist-info`, exakt Synologys Namensmuster für
  Sync-Konflikte) - Dateien, die pip gerade frisch geschrieben hatte, wurden im Hintergrund von Synology Drive
  erneut anfasst/ersetzt, was zu ungültigen/unlesbaren Paketzuständen führte. Betroffen war nicht nur
  `pillow-heif` selbst, sondern auch das bereits vorher funktionierende `pillow` - mehrfach musste die venv erst
  wieder in einen lauffähigen Ausgangszustand zurückversetzt werden (manuelles Entfernen der kaputten
  `dist-info`-Ordner + Neuinstallation), bevor der nächste Versuch überhaupt möglich war.
- Das Muster: direkt nach einer Neuinstallation funktioniert der Import einwandfrei, schlägt aber nach einigen
  Sekunden Wartezeit (vermutlich wenn Synology Drive im Hintergrund nachsynchronisiert) mit dem Stale-Handle-
  Fehler fehl - unabhängig davon, ob danach überhaupt etwas an den Dateien geändert wurde.
- **Fazit**: `.venv`-Ordner, die direkt im Synology-Drive-Sync-Pfad liegen, sind für `pip install` grundsätzlich
  nicht zuverlässig - das deckt sich mit dem bereits bekannten `tsx watch`-Problem aus der Backend-Doku
  ("hängt sich auf, vermutlich wegen Synology-Drive-Sync + FSEvents"), betrifft hier aber sogar einmalige,
  abgeschlossene Install-Vorgänge, nicht nur dauerhaft laufende Watcher-Prozesse.

Die lokale `ml-service/.venv` wurde nach jedem Versuch wieder in einen sauberen, funktionierenden
Ausgangszustand zurückversetzt (`pillow==10.4.0`, kein `pillow-heif` installiert, `torch`/`face_recognition`
laufen nachweislich) - **sie enthält aktuell noch NICHT** `pillow-heif`, obwohl es jetzt in
`requirements.txt` steht.
